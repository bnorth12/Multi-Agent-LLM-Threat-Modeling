# GUI Requirements

Date: 2026-05-03
Status: Draft v0.1

**HMI Architecture Blueprint:** [docs/HMI_Architecture_Blueprint.md](../docs/HMI_Architecture_Blueprint.md) is the design authority document that implements these requirements. Refer to it for navigation model, shared component patterns, screen wireframes, role-based access gating, and state management. S05-04 HITL gate implementation SHALL conform to the blueprint.

Purpose:

- Define graphical user interface requirements for all analyst-facing interactions
- Cover input entry, HITL gate screens, pipeline status, stage results, export, snapshot management, and agent prompt configuration
- Establish GUI access control alignment with system authorization policy

Planned sprint: future sprint (post Sprint 2026-05)

Related requirements:

- PRJ-006, PRJ-011, PRJ-012, PRJ-014, PRJ-016, PRJ-017, PRJ-018, PRJ-021, PRJ-022
- HITL-001 through HITL-011
- INT-006, INT-007, INT-008, INT-009, INT-010, INT-011, INT-013

|ID|Name|Requirement Text|Requirement Rationale|Verification Method|Verification Statement|
|---|---|---|---|---|---|
|GUI-001|Input Entry Form|The GUI SHALL provide a form-based input screen for analyst entry of system name, description, data flows, assets, trust boundaries, and deployment context prior to pipeline execution.|A structured entry form reduces input errors and ensures all required fields are captured before analysis begins.|Demonstration|Verified by walkthrough confirming all required input fields are present and submitted payload passes schema validation.|
|GUI-001A|Pipeline Auto-Execution After Form Submission|The GUI SHALL automatically invoke the threat modeling pipeline (all 9 agents) immediately upon successful form submission and file validation, without requiring an additional explicit "Start Pipeline" button or user action.|Auto-execution of the pipeline is a core functional requirement to enable the end-to-end threat modeling workflow and fulfill GUI-003 real-time execution monitoring.|Test|Verified by form submission triggering pipeline execution as evidenced by stage progress updates, agent message log population, and artifact generation (canonical graph, STIX bundle, Mermaid diagram, markdown report).|
|GUI-002|HITL Gate Screens|The GUI SHALL provide a dedicated screen for each HITL gate that presents the relevant stage outputs, supports approve, edit, and override actions, and captures rationale for all non-approve decisions.|Gate screens must give analysts full context and decision controls to meet HITL governance requirements defined in HITL-001 through HITL-011.|Demonstration|Verified by walkthrough of each defined gate screen confirming context display and all required action controls are present.|
|GUI-002A|Human-Readable Gate Artifact Rendering|The GUI SHALL render gate-review artifacts in human-readable summaries in addition to raw structured payloads, including counts, labels, subsystem or interface names, and concise automated checks relevant to the gate under review.|Reviewers need readable summaries for fast triage; raw JSON alone is insufficient for efficient analyst validation even when schema-valid.|Test|Verified by Gate 1 review showing system context, subsystem summary, interface preview, and automated review checks alongside the raw artifact payload.|
|GUI-002B|Non-Blocking HITL Gate Resume|The GUI SHALL execute HITL gate resume actions in a non-blocking background thread so that the Streamlit UI thread is not blocked during resumed pipeline execution. The run registry status SHALL transition to RUNNING while resumption is in progress, and the pipeline status dashboard SHALL display live stage progress updates during resumed execution in the same manner as the initial run.|Blocking the UI thread during resume prevents navigation, causes Streamlit to appear frozen, and prevents the dashboard from providing situational awareness during the resumed execution segment. This extends GUI-001A (non-blocking start) to cover the resume path.|Test|Verified by triggering gate resume and confirming: (1) UI remains navigable during resumed execution, (2) Home dashboard shows RUNNING status and stage progress updates during the resumed run, (3) dashboard transitions to COMPLETED or next PAUSED state on completion.|
|GUI-003|Pipeline Status Dashboard|The GUI SHALL provide a pipeline status view that displays the current executing stage, completed stages, pending stages, and any blocking conditions in real time during execution.|Analysts need situational awareness of pipeline progress to manage review timing and escalate blockers promptly.|Demonstration|Verified by executing a full run and confirming the status view updates at each stage transition.|
|GUI-003A|Gate-Aware Pause Visibility|When execution is paused by a HITL gate, the GUI SHALL display the gate identifier, gate status, and count of completed stages, and SHALL not present the paused state as a runtime failure.|Clear differentiation between expected HITL pauses and actual failures is required for safe operator decision-making and accurate incident triage.|Test|Verified by triggering Gate 1 pause and confirming dashboard display of paused gate metadata without generic execution-failure messaging.|
|GUI-003B|Screen-Level Execution State Synchronization|Every GUI screen SHALL synchronize pipeline execution state from the process-level run registry at the start of each render pass before displaying screen content. This synchronization SHALL apply to all screens including but not limited to: Home dashboard, Stage Results, Threat Review, Results Export, and Snapshot Manager.|Background thread execution updates the run registry independently of Streamlit session state. Without explicit synchronization at each screen render, screens that are navigated to during or after a background run will display stale or empty state, causing screens such as Results Export and Snapshot Manager to falsely indicate no run is available.|Test|Verified by starting a background run, navigating to each screen during and after execution, and confirming each screen reflects current run state without requiring a manual refresh or navigation cycle.|
|GUI-003C|Cross-Screen State Coherence During and After Background Execution|All GUI screens that display run artifacts (Results Export, Snapshot Manager, Threat Review, Stage Results) SHALL present state consistent with the most recently completed or in-progress background execution and SHALL NOT display stale pre-run or pre-resume state when a completed or in-progress run exists in the run registry.|Stale state on artifact screens causes operators to silently work with empty or pre-run data, resulting in incorrect exports, incomplete snapshots, and missed threat review content. This requirement extends GUI-003B by explicitly asserting the correctness invariant for artifact screens.|Test|Verified by: (1) completing a background run, (2) navigating to Results Export and confirming all four artifact downloads reflect run output, (3) navigating to Snapshot Manager and saving a snapshot, (4) confirming saved snapshot contains non-empty pipeline_state matching the completed run.|
|GUI-004|Stage Results Viewer|The GUI SHALL provide a results viewer for each pipeline stage that renders the stage output artifacts and makes them accessible to the analyst before and after HITL review.|Per-stage visibility is required for analyst calibration, auditing, and review between gates.|Demonstration|Verified by navigating to each stage result view during and after a run and confirming stage output is rendered correctly.|
|GUI-005|Threat and Mitigation Review Screen|The GUI SHALL provide a combined threat and mitigation review screen that renders scored threats alongside their mapped mitigations and supports inline approval and edit actions per threat record.|Threat and mitigation review is a primary analyst workflow and requires consolidated context to support efficient and accurate decisions.|Demonstration|Verified by review screen walkthrough confirming threat scores, mitigation mappings, and inline edit controls are all present and functional.|
|GUI-006|Results Export Interface|The GUI SHALL provide an export panel that allows analysts to download completed run outputs in canonical JSON, STIX 2.1 bundle, Mermaid diagram, and Markdown report formats.|Exportable outputs in standard formats are required for downstream tooling integration and program deliverable packaging.|Demonstration|Verified by export panel walkthrough confirming all four format downloads are available, triggered successfully, and produce valid output files.|
|GUI-007|Run Snapshot Export|The GUI SHALL provide a snapshot export action that captures the complete run state, including inputs, all intermediate stage results, HITL decisions, prompt configuration, and run metadata, into a single portable file.|Snapshot export enables run archival, audit evidence packaging, session handoff, and future restore without loss of intermediate state.|Test|Verified by exporting a snapshot and confirming the snapshot file contains all required run state fields as defined by the snapshot schema.|
|GUI-008|Run Snapshot Restore|The GUI SHALL provide a snapshot restore action that imports a previously exported snapshot file and reconstitutes the run state so that the analyst can continue analysis, review history, or audit the prior run.|Restore capability supports program continuity, analyst session handoffs, and compliance evidence review across sessions.|Demonstration|Verified by restoring a snapshot into a fresh session and confirming the reconstituted run state matches the original exported state.|
|GUI-009|Agent Prompt Editor|The GUI SHALL provide an agent configuration screen that displays the current active prompt for each pipeline agent and allows authorized users to edit and save updated prompts without requiring source code changes.|In-GUI prompt editing enables mission tuning, policy updates, and operational adaptation by authorized non-developer roles and reduces deployment friction.|Demonstration|Verified by editing a prompt through the GUI and confirming that the next pipeline execution uses the updated prompt text.|
|GUI-010|Agent Prompt Version History|The GUI SHALL maintain a version history of saved agent prompts and allow authorized users to view prior prompt versions and revert to a selected prior version.|Version history prevents permanent prompt loss and enables rollback when prompt changes produce undesired or degraded behavior.|Inspection|Verified by saving multiple prompt versions for an agent, viewing the version list, and confirming the revert action restores the selected prior prompt in the next execution.|
|GUI-011|Role-Enforced GUI Access Control|The GUI SHALL enforce role-based access controls consistent with INT-013 such that edit, approve, override, export, snapshot, and agent prompt-edit actions are restricted to authorized roles and unauthorized actions are blocked at the GUI layer.|GUI access control must align with the system authorization policy defined in PRJ-012 to prevent unauthorized analyst actions through the interface.|Test|Verified by role matrix tests confirming that actions requiring elevated roles are blocked for unauthorized roles and permitted for authorized roles at the GUI layer.|
|GUI-012|Model Provider Selection Screen|The GUI SHALL provide a model configuration screen that displays available model providers (local, hosted cloud services, commercial API services), allows analysts to select a provider, and presents provider-specific connection options without requiring source code changes. The configuration screen SHALL also include pipeline stage selection controls that allow analysts to enable or disable individual pipeline stages (agent_01 through agent_09) via checkbox controls, with validation requiring at least one stage to remain enabled.|Analyst-driven model provider selection enables runtime flexibility to switch between local LLMs, cloud-hosted instances, and commercial services based on mission constraints and availability. Stage selection controls allow analysts to tailor pipeline execution by skipping stages not relevant to the current analysis scope.|Demonstration|Verified by walkthrough confirming (1) all available provider options are displayed, (2) selection is retained and the next pipeline execution targets the selected provider, (3) all 9 pipeline stages are visible with checkbox controls, (4) analysts can enable/disable stages, (5) stage selection persists after Apply Settings, and (6) configuration prevents saving with zero stages enabled.|
|GUI-012A|Pipeline Stage Selection Controls|The GUI SHALL display all 9 pipeline stages (agent_01 through agent_09) with human-readable labels and individual checkbox controls for enabling/disabling each stage. At least one stage must remain enabled at all times. Stage selection changes SHALL persist after clicking Apply Settings and SHALL be recovered on subsequent visits to the configuration screen.|Analysts require granular control over which stages execute in a pipeline run to support scope-limited analysis, stage-specific debugging, and resource-constrained deployments. Checkbox controls provide clear, unambiguous selection state for each stage.|Test|Verified by opening Pipeline Configuration, confirming all 9 stages display with correct labels and checkboxes, disabling and enabling stages, clicking Apply Settings, reloading the page, and confirming selected state persists. Validation error SHALL display if all stages are unchecked before Apply Settings is clicked.|
|GUI-013|Model Connection Details Configuration|The GUI SHALL provide a configuration form for entering and editing model connection details including API endpoint, API key, authentication credentials, model name, deployment ID, and region-specific settings, with secure storage of sensitive credentials (encrypted or credential manager integration).|Connection detail configuration enables seamless integration with diverse model instances without code modification or manual config file editing.|Demonstration|Verified by entering connection details for a hosted LLM provider through the form, confirming data is persisted, and confirming the next run uses the configured endpoint and credentials.|
|GUI-014|Model Connection Validation|The GUI SHALL provide a test-connection action that validates model connectivity and authentication before commencing a pipeline run, returning a user-readable status message and blocking run initiation if validation fails.|Pre-execution validation prevents pipeline failures due to misconfigured endpoints or expired credentials and provides immediate feedback for configuration troubleshooting.|Test|Verified by test-connection action with valid and invalid credentials, confirming success message on valid connection, clear error message on invalid, and run-blocking behavior on failed validation.|
|GUI-015|Token Usage Telemetry Dashboard and Export|The GUI SHALL provide a token usage screen that reports per-stage and aggregate token usage metrics (prompt, completion, reasoning, cached, total, request count) for live LLM runs, and SHALL provide export of token usage data as a run artifact for verification evidence.|Operational verification requires objective proof that live provider calls occurred and consumed tokens. Per-stage visibility also supports model tuning, cost tracking, and gate-stage diagnostics.|Test|Verified by executing a live xAI run and confirming non-zero totals on the Token Usage screen, stage-level usage rows for agent_01 through agent_09, and downloadable token usage JSON artifact from Results Export.|
|GUI-016|Backend Runtime State Projection|The GUI SHALL render execution status, provider mode, and gate/stage progress from backend asynchronous runtime-state projections and SHALL NOT rely on screen-local session state as authoritative runtime state.|Backend-projected runtime state ensures that all screens show coherent status during asynchronous execution, refresh, and multi-screen navigation.|Test|Verified by executing a background live run, navigating all screens, performing browser reload, and confirming each screen reports identical run/provider status from backend state projection.|
|GUI-017|Live Mode Failover Hard-Stop Visibility|If a run configured for live LLM mode degrades to fixture/offline mode, the GUI SHALL display a hard failure status and explicit fallback reason, and SHALL report execution as halted.|Operator trust and verification integrity require immediate and visible failure when live mode is no longer being honored.|Test|Verified by inducing fallback during a live-intent run and confirming FAILED status, explicit fallback error message, and halted stage progression in dashboard and review screens.|
|GUI-018|STIX Threat Model Viewer|The GUI SHALL provide a dedicated STIX viewer that renders the generated STIX 2.1 bundle with object grouping (attack-pattern, course-of-action, relationship) and basic search/filter controls for analyst review.|STIX bundles are large and difficult to audit in raw JSON form; structured visualization is required for analyst verification and governance sign-off.|Demonstration|Verified by loading a completed run and confirming the STIX viewer renders object groups, supports filtering by object type, and shows object counts consistent with export artifact content.|
|GUI-019|Canonical Graph Viewer|The GUI SHALL provide a dedicated canonical graph viewer that renders system, subsystem, component, function, and interface structures from the canonical graph artifact in a navigable hierarchical layout.|Analysts require first-class inspection of graph hierarchy and trust-boundary relationships without manually parsing JSON payloads.|Demonstration|Verified by opening canonical graph viewer and confirming hierarchy navigation, interface-to-node linkage visibility, and parity with exported canonical JSON content.|
|GUI-020|Mermaid Diagram Viewer|The GUI SHALL provide an in-app Mermaid diagram viewer for generated Level 0/1/2 diagram content with source-text toggle and render error visibility.|Diagram review is a primary workflow for architecture validation; analysts need rendered visual output and quick access to underlying Mermaid source.|Test|Verified by completed run showing rendered Mermaid diagrams for available levels, source toggle output, and explicit error message when invalid Mermaid syntax is present.|
|GUI-021|STRIDE Threat Model Viewer|The GUI SHALL provide a dedicated STRIDE threat model viewer that presents per-interface STRIDE scores, justifications, and associated threats in sortable tabular form.|STRIDE analysis must be reviewable independent of raw canonical JSON to support analyst calibration, audit, and sign-off workflows.|Test|Verified by completed run showing per-interface STRIDE rows (S/T/R/I/D/E), score justifications, and linked threats with sortable columns.|
|GUI-022|STRIDE Threat Model Export|The GUI SHALL provide an explicit export action for STRIDE threat model results as a standalone artifact (JSON or CSV) in addition to existing full-run exports.|A standalone STRIDE export is needed for downstream risk workflows, external reporting, and requirement-level verification evidence.|Test|Verified by exporting STRIDE artifact from GUI and confirming file contains per-interface STRIDE fields and matches data shown in STRIDE viewer.|
|GUI-023|Results Export Quick Preview Functionality|The Results Export quick preview controls SHALL expand and render artifact previews for canonical graph, STIX bundle, report, Mermaid diagrams, and token usage in the active run context.|Quick preview is an analyst efficiency feature; non-functional preview controls degrade review workflow and can mask artifact generation defects.|Test|Verified by opening each quick preview panel and confirming expected preview content renders without navigation errors for a completed run.|
|GUI-024|Component and File Version Visibility|The GUI SHALL display release-governed component semantic versions and component-file version identifiers in Results Export and Snapshot Manager views, and SHALL provide export of the same version inventories as release evidence artifacts.|Operators and auditors need direct visibility to exact component and file versions used for a run so release evidence remains traceable to implementation state.|Test|Verified by completing a run and confirming both screens display component version and file version inventories that match exported release evidence artifacts.|
|GUI-025|Markdown Viewer and Editor|The GUI SHALL provide a markdown viewer and editor to open, preview, edit, and save markdown files generated or managed by the tool, with clear save-state feedback and basic edit safeguards.|Operators need in-app markdown editing to correct run documentation, reports, and process artifacts without leaving the workflow context or using external editors.|Test|Verified by opening a generated markdown artifact, editing content, previewing rendered markdown, saving changes, and confirming persisted updates are reflected on reopen and in exported artifacts where applicable.|
|GUI-026|Run Liveness Telemetry|The GUI SHALL display live heartbeat age and the configured timeout threshold on execution status surfaces and SHALL surface backend stall failures with actionable messaging.|Operators need immediate visibility into backend liveness during live runs so hangs can be diagnosed without waiting for a generic UI timeout.|Test|Verified by running a live pipeline, observing heartbeat age and timeout threshold in the sidebar or status area, and confirming a stalled run displays a visible failure message.|
|GUI-027|Run Diagnostics Panel|The GUI SHALL provide a dedicated Run Diagnostics panel that shows status, elapsed time, run ID, stage, gate, provider, and heartbeat age in one view.|A compact telemetry panel reduces context switching and accelerates triage during live execution.|Test|Verified by starting a run and confirming the diagnostics panel renders the required fields while execution is in progress.|
|GUI-028|Execution Error Rendering|The GUI SHALL decode execution errors for readability, surface provider HTTP status codes when available, and provide the raw error payload in a copyable form for diagnostics.|Readable error output shortens investigation time and preserves exact provider context for support and debugging.|Test|Verified by inducing a provider failure and confirming the UI shows decoded text, extracted status code, and a raw-error view.|
|GUI-029|Last Prompt Response Correlation|The GUI SHALL correlate prompt text and model response by prompt record identifier on the Last Prompt screen, display only the response matching the selected prompt, and suppress stale responses from prior attempts.|Prompt/result correlation prevents stale carryover when operators switch between prompts during active use.|Test|Verified by changing selected prompts during execution and confirming only the matching response is rendered for each prompt selection.|
|GUI-030|Ordered HITL Gate Ledger|The GUI SHALL display all defined HITL gates in pipeline order on the HITL Gate page, and SHALL summarize gate lifecycle counts for Approved, Rejected, Bypassed, and Pending states without splitting the workflow into separate status-only sections.|Operators need one authoritative gate ledger to maintain situational awareness during review and resume workflows without hunting across multiple panels.|Test|Verified by rendering the HITL Gate page during active and completed runs and confirming all gate records appear in defined order with lifecycle summary counts and row-level review controls.|
|GUI-031|Persistent Timeline Status and Gate-Centric Monitoring|The GUI SHALL keep execution timeline visibility in the global footer, SHALL render centered plain-language status text for the current run state (for example, Running Input Normalizer or Paused for Input Integrity Gate), and SHALL allow operators to remain on the HITL Gate page while the run continues or resumes.|Operators should not have to navigate back to a separate execution-only page to maintain awareness of live progress or paused-gate status.|Test|Verified by resuming and observing a live run from the HITL Gate page and confirming the centered footer status text updates while the active page remains unchanged.|
|GUI-032|Input Integrity Preflight Review Gate|The GUI SHALL enforce review of a preflight Input Integrity gate before Stage 1 execution proceeds, SHALL present parsed input intent and integrity checks in human-readable form (including source presence, text and table summaries), and SHALL require explicit approve or reject decisions with analyst rationale.|Early preflight review reduces downstream model drift and catches malformed or unintended source inputs before they are sent to the Stage 1 LLM workflow.|Test|Verified by starting a run with HITL enabled and confirming Gate 0 pauses execution prior to Stage 1 until an analyst approves or rejects after reviewing preflight summaries and checks.|
|GUI-033|Post-Stage-1 Normalization Review Gate|The GUI SHALL enforce a dedicated normalization review gate immediately after Stage 1 and before Stage 2, SHALL render a human-readable summary of normalized canonical graph content (system, counts, interfaces, and validation checks), and SHALL block Stage 2 execution until approve or reject decision is submitted.|A post-normalization control point ensures Stage 2 consumes an analyst-validated initialization baseline rather than unreviewed Stage 1 model output.|Test|Verified by executing a HITL-enabled run and confirming Stage 1 completion opens a normalization review gate, Stage 2 remains blocked until approval, and rejection halts the run with recorded rationale.|
|GUI-034|Mermaid Multi-Diagram Review Workspace|The GUI SHALL parse Mermaid artifact payloads into a selectable diagram list, SHALL show the selected diagram in rendered and source-editable forms with toggleable split/diagram/text display modes, and SHALL display a position indicator with selection name (`x of n - diagram name`).|Analysts need deterministic navigation across multiple generated diagrams and direct source-to-render parity when validating architecture views and diagram quality.|Test|Verified by loading Mermaid artifacts containing multiple diagrams and confirming selectable named entries, split and single-pane mode toggles, editable source text synchronization, rendered preview updates, and visible `x of n` indicator metadata.|
