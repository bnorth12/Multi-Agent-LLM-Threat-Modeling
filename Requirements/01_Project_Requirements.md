# Project Requirements

|ID|Name|Requirement Text|Requirement Rationale|Verification Method|Verification Statement|
|---|---|---|---|---|---|
|PRJ-001|Unified Input Ingestion|Threat Modeler SHALL ingest tabular interface data (CSV or Excel) describing interfaces between subsystems, components, and functions, and narrative documents (text or structured format) describing the system, its subsystems, components, and functions, in a single analysis run.|Unified ingestion of both interface data and narrative descriptions is required for practical analyst workflows where system structure and interface behavior are captured in separate source documents.|Demonstration|Verified by executing an end-to-end run with tabular interface input and narrative description input and confirming both sources are present in run artifacts.|
|PRJ-002|Canonical Graph Authority|Threat Modeler SHALL produce a canonical threat-model graph as the authoritative run artifact.|A single source of truth prevents cross-artifact drift.|Inspection|Verified by artifact review showing all downstream outputs reference canonical graph IDs.|
|PRJ-003|Deterministic Pipeline|Threat Modeler SHALL execute a deterministic multi-agent pipeline with auditable stage boundaries.|Determinism is required for repeatability and accreditation.|Test|Verified by repeated identical runs producing equivalent stage outputs and transition logs.|
|PRJ-004|Stage Validation Gate|Threat Modeler SHALL validate every stage output against a defined schema before downstream processing.|Validation prevents error propagation.|Test|Verified by injecting malformed stage output and confirming downstream stages are blocked.|
|PRJ-005|Full Threat Workflow|Threat Modeler SHALL perform trust-boundary analysis, STRIDE scoring, threat generation, mitigation mapping, STIX packaging, diagram generation, and report generation for each completed run.|The workflow defines project mission scope.|Demonstration|Verified by completed run containing all required stage outputs.|
|PRJ-006|HITL Governance|Threat Modeler SHALL support human-in-the-loop approval, edit, and override gates at defined decision points.|Analyst control is required for high-consequence systems.|Demonstration|Verified by gate workflow walkthrough showing approve, edit, and override actions.|
|PRJ-007|Immutable Auditability|Threat Modeler SHALL maintain immutable run history with who, what, when, and why metadata for all analyst edits.|Compliance and forensics require immutable provenance.|Inspection|Verified by review of audit logs containing actor, timestamp, rationale, and before-and-after diff.|
|PRJ-008|Configurable Model Selection|Threat Modeler SHALL support configurable model-provider selection through configuration without source-code changes.|Provider agility reduces integration risk.|Test|Verified by switching provider configuration and running without code modification.|
|PRJ-009|Deployment Mode Flexibility|Threat Modeler SHALL allow deployment in offline-only mode and policy-approved hybrid mode.|Deployment constraints vary by program classification.|Analysis|Verified by configuration and architecture review showing both modes and policy controls.|
|PRJ-010|Evidence-Linked Outputs|Threat Modeler SHALL provide retrieval-augmented evidence references for generated threats and mitigations when knowledge bases are enabled.|Traceable evidence improves analyst trust and review speed.|Test|Verified by threat and mitigation records including source references when retrieval is enabled.|
|PRJ-011|Export Artifact Set|Threat Modeler SHALL produce exportable outputs for canonical JSON, STIX 2.1, Mermaid diagrams, and final markdown report.|Output interoperability is required for downstream tooling.|Demonstration|Verified by successful export of all four artifact types in one run.|
|PRJ-012|Role-Based Access Control|Threat Modeler SHALL enforce role-based permissions for author, reviewer, and approver actions.|Controlled actions are required for governance and separation of duty.|Test|Verified by permission tests confirming blocked unauthorized actions and allowed authorized actions.|
|PRJ-013|Incremental Enrichment|Threat Modeler SHALL support incremental model enrichment without destructive overwrite of previously approved data.|Programs evolve and require safe incremental updates.|Test|Verified by merge run preserving approved prior elements while adding new scope.|
|PRJ-014|Selective Re-Run|Threat Modeler SHALL provide selective re-run from an analyst-selected stage after approved edits.|Selective re-run reduces cycle time.|Demonstration|Verified by restarting from selected stage and confirming prior unchanged stages are not recomputed.|
|PRJ-015|Fail-Safe Halting|Threat Modeler SHALL fail safely by halting downstream execution when critical validation errors are detected.|Safe failure prevents invalid outputs from release.|Test|Verified by induced critical validation failure causing controlled stop with error report.|
|PRJ-016|Analyst Graphical Interface|Threat Modeler SHALL provide a graphical user interface for all analyst-facing interactions including system input entry, HITL gate review, pipeline status monitoring, stage result review, and output export.|A GUI is required for operational usability and to support non-developer analyst roles without requiring command-line access.|Demonstration|Verified by walkthrough confirming all analyst interaction workflows are accessible and functional through GUI screens.|
|PRJ-017|Run Snapshot Portability|Threat Modeler SHALL support export and import of complete run state snapshots that capture inputs, all intermediate stage results, HITL decisions, prompt configuration, and run metadata.|Snapshot portability is required for run archival, analyst session handoff, and audit evidence packaging across sessions.|Test|Verified by exporting a run snapshot, importing it in a fresh session, and confirming the reconstituted state matches the original.|
|PRJ-018|Agent Prompt Configurability|Threat Modeler SHALL allow authorized users to view, edit, save, and revert each agent prompt through a GUI without requiring source code changes, and SHALL maintain a version history of saved prompt configurations.|Operational prompt tuning by non-developer roles reduces deployment friction, enables mission adaptation, and supports rollback of undesired prompt changes.|Demonstration|Verified by editing and reverting agent prompts through the GUI without modifying source code and confirming updated prompts are used in subsequent pipeline executions.|
|PRJ-019|Asynchronous Backend State Authority|Threat Modeler SHALL maintain authoritative runtime execution and provider state in a backend asynchronous state service, and GUI screens SHALL consume this state as read projections rather than owning the runtime source of truth.|A backend-owned runtime state model prevents cross-screen drift and reload loss, and enables reliable concurrent read access by GUI and backend workflows.|Test|Verified by starting a live run, navigating across all GUI screens and reloading the browser, and confirming run/provider state remains consistent without reconfiguration. **Implementation:** `backend/run_manager.py` (execution registry and thread management), `backend/prompt_store.py` (prompt state persistence), `ui/execution.py` (Streamlit adapter, reads from `run_manager.get_run_status()`). JSON persistence: `~/.multi_agent_threat_modeler_runs.json` and `~/.multi_agent_threat_modeler_prompts.json`. Sprint 2026-09 delivery confirmed 2026-05-11; 259 unit tests passing.|
|PRJ-020|Live-Mode Integrity Halt on Provider Degradation|When configured for live LLM mode, Threat Modeler SHALL detect any fallback to offline fixture/static execution and SHALL halt execution in a failed state with explicit error details.|Silent degradation from live to fixture mode invalidates verification evidence and can conceal provider/runtime defects.|Test|Verified by inducing live-mode fallback conditions and confirming immediate run failure with stage context and fallback reason, while explicit fixture-mode runs continue normally.|
|PRJ-021|Component Semantic Version Authority|Threat Modeler SHALL maintain an explicit semantic version for each major component (agents, orchestrator, HITL service, UI module groups, and export services), and release candidate approval SHALL require a versioned component manifest included in release artifacts.|Component-level semantic versions are required for release governance, compatibility analysis, and controlled rollback when defects are discovered after release.|Inspection|Verified by reviewing release candidate artifacts and confirming a component version manifest exists, lists all required components, and reflects changes introduced in the sprint.|
|PRJ-022|Component File Version Traceability|Threat Modeler SHALL maintain deterministic per-file version identifiers for all component-owned source files, and each release candidate SHALL include a file-level version inventory mapped to component versions.|File-level version identifiers provide fine-grained provenance so releases can be audited to exact file revisions and quickly diffed during incident response or accreditation review.|Test|Verified by generating a file-level version inventory during release candidate build, confirming each tracked file has a version identifier, and validating mapping consistency against the component manifest.|
|PRJ-023|LangGraph Native Orchestration|Threat Modeler SHALL provide and support a LangGraph StateGraph runtime path for multi-stage pipeline routing, while preserving validation and HITL gate semantics. Release validation profiles SHALL execute with `execution_mode=langgraph-compatible`.|Native orchestration removes migration debt and provides deterministic graph execution semantics for future branching/checkpoint extension.|Test|Verified by unit/integration tests showing stage progression, validation halts, and gate behavior on the LangGraph-backed orchestrator path, plus release-profile configuration evidence that `execution_mode=langgraph-compatible` is used for governed validation runs.|
|PRJ-024|Visible Browser CAV Upload Validation Workflow|Threat Modeler SHALL provide an automated visible-browser validation workflow that uploads CAV fixture files (ICD plus markdown narratives) through the Input Entry UI and verifies files are loaded into the run input workflow.|This provides repeatable analyst-facing UI evidence for browser upload behavior tied to live-run validation campaigns.|Demonstration|Verified by executing the visible-browser automation flow and confirming CAV ICD + markdown fixture file names are rendered by the UI uploader prior to run initiation.|
|PRJ-025|Operational Runtime Without Streamlit|Threat Modeler SHALL provide an operational web/API runtime that does not require Streamlit, and SHALL reserve Streamlit usage for automated browser-validation workflows only.|Separating operational runtime from Streamlit removes UI framework coupling from deployed environments while preserving GUI evidence automation in test campaigns.|Test|Verified by launching `python -m threat_modeler` and interacting with runtime endpoints without importing Streamlit, while e2e browser tests continue to launch Streamlit from test-only dependencies.|
|PRJ-026|Inter-Agent Handoff Integrity|Threat Modeler SHALL pass approved outputs between agents through canonical handoff records that preserve stage output version, correlation identifier, and compliance metadata, and SHALL not alter approved content except through an explicit analyst or validation decision.|Stable inter-agent handoff is required so downstream stages receive exactly the approved upstream artifact and audit records remain traceable.|Test|Verified by full pipeline runs and handoff inspection confirming each stage consumes the prior approved canonical output and records stage boundary metadata.|
|PRJ-027|ICD Source Compliance Validation|Threat Modeler SHALL validate ICD spreadsheet input and narrative source documents for required structure, source provenance, and cross-reference consistency before downstream agent handoff, and SHALL surface non-compliance as a structured validation failure or HITL gate condition.|ICD-compliant source handling prevents downstream stages from analyzing malformed or mis-mapped engineering data.|Test|Verified by input-validation tests and browser upload runs that confirm source documents are accepted only when required structure and provenance checks pass.|
|PRJ-028|Orchestrator Gate Enforcement and Resume Control|Threat Modeler SHALL have the orchestrator pause execution at HITL gates, persist the gate decision state and rationale, block downstream processing until an approved decision is recorded, and resume from the correct checkpoint only after acceptance.|Gate enforcement is required so human approvals are authoritative and downstream execution cannot bypass governance decisions.|Test|Verified by gate pause/resume tests confirming paused state, recorded decision, checkpoint preservation, and controlled continuation after explicit approval.|
|PRJ-029|Live Run Liveness Fail-Closed|Threat Modeler SHALL monitor live LLM execution for backend heartbeat staleness and SHALL halt the run in a failed state before the UI timeout elapses when liveness is lost, with an actionable error message.|Opaque stalls make live execution unreliable and conceal provider/runtime failures from analysts.|Test|Verified by inducing a stalled live run, confirming heartbeat expiry is detected, and confirming the run transitions to FAILED with a visible stall message.|
|PRJ-030|Prompt Store Authority and Fail-Closed Loading|Threat Modeler SHALL treat the backend prompt store as the authoritative source for agent prompt configuration and SHALL not silently fall back to file defaults when prompt loading fails; prompt persistence and retrieval errors SHALL be surfaced explicitly.|Prompt edits are only trustworthy when they are written through the backend execution path and failures are visible to operators.|Test|Verified by editing prompts through the GUI, confirming backend persistence is used during execution, and confirming prompt-load failures produce explicit errors rather than silent defaults.|
